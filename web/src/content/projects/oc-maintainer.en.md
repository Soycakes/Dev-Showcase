This project connects a running game to a live web app. Lua scripts on in-game computers read the state of a modded Minecraft storage network and push it to a web server, the server streams it to a browser in real time, and anything you change in the browser flows back into the game as crafting requests. From a phone or a second monitor you can watch hundreds of items and control what the game keeps stocked, without being logged into the game at all.

The game side is two OpenComputers computers running Lua. One talks to the Applied Energistics 2 storage network, reads stock counts, queues crafting jobs, and handles items, fluids and essentia. The other is a bridge that relays that state to my web server over HTTP, and the two computers talk to each other through a linked card. Every few seconds the first one polls the network and requests whatever crafts are needed, and the bridge syncs the result out.

On the other side is a Node.js server with Express. It stores everything in SQLite (WAL mode, with every write inside a transaction) and pushes changes to open browsers over WebSocket, so stock numbers reach the page with sub second latency. I designed the whole API between the game, the server and the browser myself: the sync endpoint the in-game connector uses, CRUD for the maintained items, bulk import, settings, groups and session auth.

The frontend is vanilla JavaScript bundled with Vite, with no framework, and the look is hand written CSS in the style of Minecraft's own UI: pixel button states, sprite atlas icons, sticky table headers and animated toasts. The most interesting frontend problem was the sort view. You can drag items into bracket groups, similar to how the NEI Calculator mod groups a recipe, collapse a group into a single row, rename it, and reorder everything with the HTML5 Drag and Drop API. I did all of that state handling without a state library, and the bracket connectors are drawn with CSS pseudo elements and absolute positioning so they never touch the table layout.

A single hosted instance can serve several players, each with their own AE2 network. Each network gets its own key, and both the in-game connector and the browser use that same key to authenticate, so there is no separate account system. Sessions, data and WebSocket updates are scoped per network, so one player never sees another's items. Older installs that were single player upgrade to the multi tenant schema through additive ALTER TABLE fallbacks, with no data lost, and the same codebase runs as a local install or a hosted server depending on environment flags. Locally on Windows, `start.bat` is all a singleplayer user needs.

Since it can be put on the public internet, I hardened the server. Login is limited per IP to 10 attempts every 5 minutes, and all API traffic to 60 requests a minute per IP. Session tokens are stored hashed, an IP blocklist can be set through an environment variable, and the cookie flags (httpOnly, sameSite, secure) are set correctly for the protocol in use.

A player can also export their whole setup, meaning items, groups, sort order and settings, to the clipboard or a file and import it on another machine or share it with someone else. The clipboard version is compact and the file version is pretty printed.

For deployment there is a multi stage Docker build that compiles the client into a small production image, with a mounted volume for the SQLite database. A Railway template deploys it in one click, configured for a single replica because SQLite needs it. Playtesting shaped much of the interface: collapsible groups, custom sort order that persists, and status colors that update live all came from watching people use it.
