MAPDev is a self-hosted harness where a group of AI agents argue about your problem in a chat room before anything gets answered. Most agent tools hand you a final answer and hide how they got there. I wanted the reasoning to be something you can read, so every agent's contribution shows up as it happens.

It came out of a frustration with agents. Earlier setups I tried would tell me they had done something they had no permission or ability to do, or get stuck repeating the same step. Role boundaries blurred, pipelines stalled halfway, and I couldn't see where. Prompt tweaks only moved the problem around, so I built the control layer myself: fixed roles, fixed order, and a way to watch every step.

Here is what happens when you send a message. A Gemini Flash coordinator reads it and decides which agents should work on it. Those agents run in parallel. A Minimalist looks for what can be cut. A Pragmatist looks for the fastest path that works. A Cynic tries to disprove both, and a Clean Code reviewer checks standards. Proposer and examiner agents run concurrently in multiple rounds, and a Lead Architect pass then synthesizes everything into the final answer. The agents' outputs sit in collapsible debate cards above that answer, so you can follow the argument and not just read the conclusion.

All of it streams to the browser over Server-Sent Events, token by token, using a typed envelope for each kind of update: tokens, a worker starting or finishing, a worker's tool call, roster changes, coordinator messages, done and error. The frontend assembles them as they arrive, so agent status lights and debate cards update live while the pipeline runs. I picked SSE over WebSockets to keep the server stateless per request and to avoid polling.

Agents also read the codebase, through a ReAct tool-use loop with a file cache shared across all of them. Each file read is pushed to the frontend through an asyncio.Queue the moment it happens, so you can see which files an agent is looking at. File access is sandboxed. Paths resolve inside a workspace jail with a denylist, so an agent can't walk out of the project directory or read sensitive files.

The hardest problem was hallucination. Agents kept referring to things in the codebase that didn't exist. I added an auditor layer that checks claims against the real codebase, and I extract the actual routes with AST parsing and inject them straight into each worker's context. That cut hallucinated references by about 90%.

You can also attach images to a message: paste from the clipboard, upload a file, or take a snapshot from a webcam (F2 as a shortcut, with device selection remembered between sessions). Images are resized and re-encoded in the browser with the Canvas API before they are sent. Only the coordinator sees the raw image. It writes a text description, and that description is what goes into each worker's context, so the workers reason about the image without receiving any image bytes and the per-worker cost stays flat.

Work is organized in projects, each with named channels. Everything is stored in SQLite, including message history and image attachments, and a channel can be forked to try a different direction without losing the original thread. Prompt presets let you write standing instructions, either global or for one project. The active preset is prepended to every agent call, which is how you tell the agents once that you are working on a competitive programming problem or that answers should be in a certain language.

Rendering the stream took more work than I expected. Chat messages go through markdown with LaTeX math (KaTeX) and syntax highlighting, and the tokens arrive in pieces. Mention detection, math parsing and incremental assembly kept fighting each other, and formatted answers would silently fall back to plain text halfway through a stream.
The backend is covered by a 104-test pytest suite over the graph nodes, verifiers and tool utilities, with every LLM call stubbed. It runs in CI with no API key, including tests that scale the number of agents and check graph routing and sandbox execution. The Claude API client is wired in as the execution layer, ready for a handoff from the planning pipeline. The original LangGraph CLI version of the pipeline is kept next to the FastAPI system as a reference. That version grew out of my earlier project, SoyLangGraph.
