## 서버가 심판입니다

Go 서버가 모든 전투를 시뮬레이션해서 이벤트 목록을 보내고, Unity 클라이언트는 그 목록을 애니메이션으로 재생만 합니다. 클라이언트가 전투 결과를 정하지 않으니 플레이어가 결과를 조작할 수 없고, 전투 구현도 하나만 관리하면 됩니다.

처음부터 이랬던 건 아닙니다. 첫 버전은 공유 시드로 클라이언트가 전투를 직접 다시 계산하는 방식이었습니다. 네트워크로 보낼 게 거의 없다는 장점이 있었죠. 하지만 같은 전투 규칙을 Go와 C#으로 두 번 짜야 했고, 동기화 불일치를 끝없이 쫓다 보니 양쪽 코드 모두 점점 나빠졌습니다. 그래서 이 방식을 버리고, 전투와 애니메이션 데이터를 서버가 작게 보낼 수 있게 포장하는 쪽에 힘을 썼습니다. 대역폭은 그대로 작게 유지하면서 중복된 시뮬레이터도 없앨 수 있었습니다.

## 카드는 스프레드시트의 행입니다

모든 능력은 데이터 한 줄입니다. 트리거(언제), 액션(무엇을), 타겟(누구에게), 그리고 몇 개의 숫자로 이루어집니다. `OnBattleStart, Buff, RandomAllies, 2, 2` 같은 줄은 "전투 시작 시 무작위 아군 둘에게 +2를 준다"라고 읽습니다. 카드별 스크립트는 없습니다. 170장이 넘는 카드(사도 79, 아티팩트 51, 스펠 34, 토큰 5)와 영웅 44명이 모두 이렇게 만들어져 있고, 4성 고학년 스킬, 6성 어사이드, 사용 횟수 제한, 중첩되는 아티팩트도 같은 방식입니다. 파이썬 스크립트가 디자인 스프레드시트를 게임이 읽는 JSON으로 바꿔 주기 때문에, 새 카드를 만들 때 코드를 건드릴 일이 없습니다.

![사도 시트, 한 줄에 효과 하나|full](/Dev-Showcase/media/SPK_28_minion_sheet.webp)

시트가 기준이 되는 원본입니다. 카드 하나는 몇 줄로 이루어지고 한 줄에 효과 하나가 들어갑니다. 스킬 종류에 따라 색이 다른데, 파란색은 기본 능력, 주황색은 고학년 스킬, 보라색은 어사이드입니다. 트리거, 액션, 타겟은 드롭다운으로 고르고, 애니메이션까지 열 하나로 들어 있어서 효과마다 자기 클립을 직접 지정합니다. Go 테스트가 모든 카드 파일을 검사하기 때문에 잘못된 행은 게임에 닿기 전에 걸러집니다. 아래는 제가 새 항목을 추가하면서 세트별로 색을 입히는 트리거와 액션 목록, 그리고 밸런싱 시트입니다.

![세트별로 색을 입힌 트리거와 액션 목록](/Dev-Showcase/media/SPK_10_sheet_triggers_actions.webp)
![카드 시트 밸런싱을 막 시작했을 때](/Dev-Showcase/media/SPK_06_sheet_balancing.webp)

상점과 전투는 디스패처 하나, 핸들러 한 세트를 같이 씁니다. 그래서 버프가 카드를 살 때나 전투 도중이나 똑같이 동작하고, 테스트 한 세트로 둘 다 확인할 수 있습니다. 화면의 카드 설명도 같은 행에서 영어, 한국어, 일본어로 만들어지기 때문에 설명과 실제 효과가 어긋날 수가 없습니다. 게임 안의 모든 설명은 툴팁 빌더 하나가 그리고, UI 코드가 카드 텍스트를 직접 만들려고 하면 빌드 스크립트가 실패하게 해 두었습니다.

## 시드 매치와 테스트 그물

상점과 봇의 모든 무작위는 매치 시드 하나에서 나오고, 라운드와 좌석별로 이름 붙은 스트림으로 나뉩니다. 같은 시드면 영웅 제시, 상점, 봇의 선택이 모두 같아서 "버그가 재현이 안 돼요"가 "시드 12345로 돌려 봐요"로 바뀌었습니다. 전역 난수를 쓰는 코드가 있으면 빌드가 실패하도록 매치 코드를 검사하는 테스트도 있습니다.

더 큰 안전망은 골든 마스터 테스트입니다. 실제 카드 풀로 만든 전투 2,000판(1성부터 6성까지, 실드, 아티팩트, 스펠, 영웅, 후반 보드 포함)을 돌려서 기록해 둔 결과와 바이트 단위로 비교합니다. 일부러 작은 버그를 심어서 잡아내는지도 확인했습니다. 여기에 모든 트리거와 액션마다 테스트가 하나씩 있고, 카드 데이터 전체 검증, 시드로 고정한 봇 매치 테스트가 더해집니다.

## 월 5달러 서버에 맞추기

성능은 별도의 프로젝트처럼 다뤘습니다. 가설 하나, 변경 하나, 벤치마크 하나, 그리고 골든 테스트 통과를 거친 것만 남겼습니다. 프로파일링해 보니 할당된 메모리의 88%가 한 곳에 몰려 있었습니다. 리플레이용으로 무엇이 바뀌었는지 계산하려고 서버가 효과를 쓸 때마다 버프 목록 전체를 복사하고 있었던 겁니다. 필요한 필드만 저장하고 바뀐 유닛만 복사하게 바꾸자 실제 전투가 3.5배 빨라지고 메모리는 5.2배 가벼워졌습니다.

이 변경에는 예상 못 한 대가도 있었습니다. 봇은 작은 전투를 돌려서 자기 수를 평가하는데, 그 경로에서는 새로 저장하는 데이터가 너무 커서 호출할 때마다 복사되었고, 그 결과 봇이 약 7% 느려졌습니다. 서버 CPU 대부분을 봇이 쓰기 때문에, 20회 비교 측정을 하고 나서 변경을 되돌렸습니다. 그리고 가벼운 전투에서는 절대 할당되지 않는 포인터 뒤로 비교용 데이터를 옮겨서 다시 만들었습니다. 실패한 시도와 그때의 판단은 성능 기록에 그대로 남겨 두었습니다.

20개가 넘는 단일 변경 최적화를 거쳐 실제 전투는 1.32ms에서 0.268ms로(4.9배 빠르게, 메모리 6.5배 절감), 가장 무거운 봇 턴은 28.5ms에서 18.3ms로(36% 빠르게, 메모리 48% 절감) 줄었습니다. 서버의 목표는 그 VPS 한 대에서 동시접속 500명이고, 모든 것이 거기서 시작했습니다.

## 실제 규칙을 따르는 봇

솔로 모드에는 난이도가 여러 단계 있습니다. 가장 쉬운 봇은 가능한 수 중에서 무작위로 둡니다. 가장 어려운 봇은 복제한 좌석에서 실제 상점 핸들러로 수를 시도해 보고, 결과마다 빠른 전투를 돌려 점수를 매깁니다. 후보를 가볍게 먼저 거른 뒤 가장 좋은 몇 개만 다시 확인하는 식입니다. 봇도 플레이어와 같은 코드를 쓰기 때문에 불가능한 수를 둘 수 없고, 새 카드가 생기면 곧바로 그 카드를 이해합니다. 봇 덱은 텍스트 덱 내보내기 파일에서 읽어 오기 때문에, 덱을 추가하려면 파일 하나를 넣기만 하면 됩니다.

### 애니메이션과 클라이언트

클라이언트는 사기, 팔기, 옮기기, 잠금 같은 간단한 상점 동작을 로컬에서 먼저 예측해서 UI가 즉각 반응하게 하고, 다음 서버 스냅샷이 오면 예측을 덮어씁니다. 전투 연출은 재사용 가능한 클립 클래스 약 40개와 JSON 항목 53개로 만들어지고, 각 항목에 어떤 클립, 스프라이트, 색, 지속 시간을 쓸지 적혀 있습니다. 클립의 길이는 서버의 매치 시계에 반영되어서, 전투가 재생되는 시간만큼 마감 시간이 잡힙니다. 클립은 트윈 빌더 기준으로 작성하기 때문에 2배, 3배 속도와 건너뛰기가 예외 처리 없이 어디서나 동작합니다. 이 방식을 깨는 클립 코드(직접 쓴 코루틴이나 시간을 직접 읽는 코드 등)는 검증 스크립트가 거부합니다.

## 계정, 래더, 보안

플레이어는 bcrypt로 해시한 비밀번호, 일회용 복구 코드를 쓰는 계정을 갖고, 모든 경로에서 세션을 검사합니다. 없는 사용자로 로그인할 때도 틀린 비밀번호와 걸리는 시간이 같아서, 공격자가 둘을 구분할 수 없습니다. IP별, 연결별 속도 제한, 실패 후 지수 백오프, 가입 수 제한, 메시지 크기와 오리진에 대한 WebSocket 제한이 있고, 사용자 이름은 저장하기 전에 비속어 필터를 거칩니다. 어디까지 막았고 무엇이 남았는지는 SECURITY.md에 적어 둡니다.

그 위에 라이브 시스템이 올라갑니다. 1v1과 4인 탭이 있는 랭크 래더, 한국 시간 새벽 4시에 지연 방식으로 초기화되는 일일 퀘스트, 재화와 보상, 저장하고 이어 할 수 있는 솔로 런(두 번째 탭이 깔끔하게 넘겨받습니다), 실시간 접속자 수를 알려 주는 하트비트가 있습니다.

## 시트와 게임을 맞춰 주는 도구들

디자인은 구글 시트에 있지만 게임은 JSON을 읽기 때문에, 데이터를 양쪽으로 옮겨 주는 작은 도구를 직접 만들었습니다. `csv_to_json.py`는 사도, 스펠, 아티팩트, 토큰, 영웅 시트를 카드 JSON 파일로 바꿔 줍니다. Unity의 JsonUtility가 없는 bool 값을 false로 읽는 것 같은 함정도 여기서 처리해서, 아티팩트는 중첩 가능 여부를 항상 명시적으로 적어 둡니다.

텍스트에는 `tools/locale.py`가 따로 있고 모드가 세 가지입니다. `generate`는 모든 카드와 영웅을 영어 로케일 파일로 읽어 들이면서 기존 키 순서를 유지하기 때문에, 시트에 다시 붙여 넣어도 행이 밀리지 않습니다. `export`는 영어, 한국어, 일본어를 CSV 하나로 내보내는데, 필터용 종류 열과 맥락 열이 있어서 시트에 바로 붙여 넣을 수 있습니다. `import`는 시트를 다시 읽어서 세 언어의 로케일 파일로 되돌립니다.

카드 텍스트는 행에서 자동으로 만들어지기 때문에, 확인하려면 직접 읽어 보는 수밖에 없습니다. 그래서 Unity 메뉴 도구 Dump Card Text가 모든 카드의 이름과, 자동 생성된 기본 설명, 고학년 스킬, 어사이드 설명을 영어와 한국어로 CSV 하나에 써 줍니다. 텍스트 템플릿을 바꾸면 git diff에서 어떤 카드가 바뀌었는지 그대로 보이고, 같은 파일을 시트에 붙여 넣어 교정도 볼 수 있습니다.

![자동 생성된 카드 텍스트, 영어와 한국어를 나란히|full](/Dev-Showcase/media/SPK_29_card_text_dump.webp)

다른 에디터 도구는 씬에서 현지화 시스템에 연결되지 않은 TextMeshPro 오브젝트를 전부 찾아 줍니다. 그래서 하드코딩된 문자열이 숨을 곳이 없습니다. UI 코드에 하드코딩되어 있던 영어 문자열을 파일, 줄 번호, 제안 키와 함께 정리한 감사 파일도 있고, 그 문자열들은 지금 시트에 키로 들어가 있습니다. `check.ps1`의 `--all` 옵션은 시트의 CSV로 JSON을 모두 다시 만들고 로케일을 가져온 다음 평소 검사를 돌립니다.

하나하나는 크지 않지만, 이 도구들 덕분에 카드를 바꿔도 JSON을 손으로 고칠 일 없이 시트에서 화면까지 바로 이어지고, 화면에 나오는 모든 문장을 교정해 볼 수 있습니다.

## 도구와 일하는 방식

전투 테스트 랩에서는 아무 보드나 직접 조작하고, 원하는 카드를 지급하고, 제출한 뒤 결과를 실제 클라이언트에서 재생해 볼 수 있습니다. PowerShell 스크립트 `check.ps1` 하나가 데이터를 Unity로 동기화하고, Go와 C#의 콘텐츠 버전이 같은지 확인하고, 애니메이션 데이터와 클립 코드를 린트하고, UI 규칙을 검사한 다음 서버를 빌드하고 테스트합니다. 이 스크립트 덕분에 이렇게 큰 코드베이스도 빠르게 바꿀 수 있습니다.

작업 내내 Claude Code를 썼고, CLAUDE.md에 누가 무엇을 결정하는지, 스타일 규칙, 검증 절차를 계약처럼 적어 두었습니다. 기술 노트, 성능, 보안, 플레이테스트 준비 문서도 계속 갱신했습니다. 설계 문서를 먼저 썼고, 그 덕분에 프레임워크와 보일러플레이트는 이틀 정도에 갖춰졌습니다. 설계를 마치고 사흘 안에 매치메이킹, 상점 단계, 전투까지 전체 루프를 돌려 볼 수 있었습니다. 에이전트가 쓴 코드는 프로젝트 규칙, 테스트, 체크 스크립트를 모두 통과해야만 들어왔습니다.

## 배포

WebGL 빌드는 Cloudflare Pages에 올라가 있습니다. 카드 아트와 오디오는 Addressables 번들로 Cloudflare R2에서 내려받고, 앞에 토큰을 확인하는 Worker를 두어서 긁어 가기 어렵게 했습니다. Go 서버는 작은 VPS에서 Cloudflare Tunnel 뒤에 있어서, 인바운드 포트를 열지 않고도 고정된 wss 주소를 쓸 수 있습니다. 데이터는 WAL 모드의 SQLite에 저장하고, Litestream으로 지속 복제하는 것은 계획 중입니다. 친구가 처음부터 빌드를 돌려 볼 수 있도록 플레이테스트와 릴리스 가이드도 써 뒀고, 실제 플레이어들과 플레이테스트도 진행했습니다.
